# 维护手册

> 适用范围: 设计系统的全部文件, 脚本, 生成物与文档  
> 事实来源: XAML 与 `scripts/check-design-system.ps1`; 生成物由 `scripts/gen-design-reference.ps1` 产出  
> 维护方式: 手写. 本手册描述流程; 具体键与值分别见[语义层](semantic-layer.md)和[全量参考](reference.md).  
> 更新触发: 校验规则, 主题结构, CI, 组件策略或文档结构发生变化时.

## 1. 维护模型

设计系统有三类产物, 修改时必须一起收敛:

| 产物     | 位置                                                                         | 性质             | 谁来改                   |
|----------|------------------------------------------------------------------------------|------------------|--------------------------|
| 代码     | `Funzor/Themes/*.xaml`, `Funzor/Views/**`, `scripts/check-design-system.ps1` | 唯一事实来源     | 手工编辑                 |
| 生成物   | `docs/design/reference.md`                                                   | 由代码生成       | 只运行脚本, 不手改       |
| 手写文档 | `docs/design/*.md` (除 reference)                                            | 解释, 边界, 流程 | 手写, 并在同一改动里更新 |

维护原则:

- **一次只做一类变更**: 改值, 加键, 改区域分开做, 方便评审和回滚;
- **两个主题一起改**: 不允许先改 Light, 以后再补 Dark;
- **先改代码, 再重生成, 最后改文档**: 文档不领先于代码;
- **生成物不进人工编辑**: 需要改内容就改脚本或 XAML;
- **文档与代码同 PR**: 不允许"下次再补文档".

角色: 变更者对完整性负责; 评审者检查区域归属, 命名, 双主题一致性, 文档同步. 即使只有一个人开发, 也按这个顺序自查.

## 2. 变更总表

| 变更类型             | 主要文件                                       | 必做校验                | 主要风险                   |
|----------------------|------------------------------------------------|-------------------------|----------------------------|
| 新增/修改原子 token  | `Tokens.xaml`                                  | DR-01, 视觉检查         | 新增孤立档位, 类型不匹配   |
| 新增/修改语义键      | `Theme.Light.xaml`, `Theme.Dark.xaml`          | DR-02 至 DR-05, DR-10   | 只改一个主题, 顺序错位     |
| 重命名语义键         | 两个主题 + 所有引用方                          | DR-09, DR-12, 全局搜索  | 漏改视图或 owner 注释      |
| 删除/废弃语义键      | 两个主题 + 引用方                              | DR-05, DR-09, DR-12     | 删除仍被引用的键           |
| 新增区域             | 两个主题 + 校验脚本                            | DR-03, DR-11            | 区块顺序, 区域权限不完整   |
| 新增视图             | 视图目录 + 校验脚本                            | DR-06 至 DR-11          | 未登记区域, 写了颜色字面量 |
| 新增控件样式         | `Controls.xaml`                                | DR-06, DR-09, 视觉检查  | 重写模板, 写死颜色         |
| 新增 Bridge 键       | 两个主题                                       | DR-12, 原生控件实际验证 | 原生键名猜错, owner 无效   |
| 新增图标             | `Icons.xaml`, `Assets/Icons/Source/`, 导航目录 | 构建, 视觉检查          | 图标 key 不存在时静默空白  |
| 新增导航分区/页面    | `NavigationCatalog`, 页面, resw, 校验脚本      | 构建, 导航与焦点检查    | 文案回退, 返回栈语义       |
| 升级 Windows App SDK | 包引用, Bridge, 白名单                         | 全量回归                | 原生键改名, 模板行为变化   |
| 修改校验规则         | `check-design-system.ps1`                      | 自测, 全仓库通过        | 规则编号漂移, 文档不同步   |

## 3. 通用步骤

### 3.1 改动前

1. 读相关文档: 区域归属看[语义层](semantic-layer.md), 值看[原子 Token](tokens.md),
   组件用法看[组件与用法](components.md);
2. 全局搜索目标键或区域, 确认是否已有相近能力;
3. 明确这次属于哪类变更, 按第 4 节的对应流程走;
4. 明确要改哪些文件, 哪些文档, 避免中途扩大范围.

### 3.2 改动后

```powershell
# 1. 设计系统规则
pwsh scripts/check-design-system.ps1

# 2. 重新生成全量参考 (改了 XAML 或校验脚本里的清单时)
pwsh scripts/gen-design-reference.ps1

# 3. 再比对一次, 确保生成物已提交且无差异
pwsh scripts/gen-design-reference.ps1 -Check

# 4. 构建
dotnet build Funzor/Funzor.csproj -c Debug -p:Platform=x64
```

然后做第 6 节的运行检查. 规则报 error 必须修; warning 要么修, 要么在 PR 里说明为什么可以接受.

### 3.3 全局搜索

PowerShell 下用:

```powershell
Get-ChildItem Funzor, scripts, docs -Recurse -File -Include *.xaml, *.cs, *.ps1, *.md |
    Select-String -Pattern 'Card.Footer.Background'
```

搜索范围至少包括: `Funzor/Themes`, `Funzor/Views`, `Funzor/Controls`, `Funzor/Helpers`, `Funzor/Navigation`, `scripts`,
`docs`. Bridge 的 owner 注释也在搜索范围内.

## 4. 键的生命周期

### 4.1 新增原子 token

1. 确认满足[新增条件](tokens.md#8-何时新增-token), 不是单页一次性值;
2. 在 `Tokens.xaml` 对应族的末尾按档位加入, 保持族内顺序; 颜色写十六进制, 度量写正确类型;
3. 运行 `check-design-system.ps1`, 确认没有 DR-01;
4. 如果只是新增值, 还没有语义键引用, 可以暂时不接入主题; 但不要把它当成"以后可能用"的批量储备;
5. 重新生成 `reference.md`;
6. 只有新增或调整了族, 档位策略时才改 `tokens.md`, 值本身不在手写文档里重复.

### 4.2 修改 token 值

1. 在 `Tokens.xaml` 改一处; 所有引用它的语义键会自动跟随;
2. 同时看 Light/Dark 下的实际效果, 尤其是文字, 边框, 状态色和悬停态;
3. 改颜色后人工检查对比度: 正文至少 4.5:1, 大字号和图标至少 3:1; 状态不能只靠颜色区分;
4. 重新生成 `reference.md`;
5. 如果值的含义变了 (例如某个色阶从"强调"变成"大面积背景"), 更新 `tokens.md` 的族说明.

### 4.3 新增语义键

1. **定区域**: 先判断用途属于哪个区域, 确认引用方有权限; 跨页面复用的按钮/表单/状态/提示走组件区域, 不新建页面区域;
2. **定命名**: 按 `{Region}.{Part}.{Property}.{State}` 组装, 最后一段必须在属性段或状态段词表里, 不能出现 `Bg`, `Fg`,
   `Color`, `Brush`, `Light`, `Dark`;
3. **查重**: 全局搜索键名和相近键, 避免同一用途出现两个键;
4. **写 Light**: 在 `Theme.Light.xaml` 对应区块中, 计划好的相邻键之后插入; 值只能引用 `A.*`;
5. **写 Dark**: 在 `Theme.Dark.xaml` 的同一个相邻键之后插入, 保持两个文件键序列完全对齐;
6. **标记预**留: 如果键为尚未实现的能力准备, 行尾加 `<!-- reserved -->`, 并在 `components.md` 的预留清单里补一行;
7. **接入使用方**: 如果本次就有视图或样式使用, 直接改引用; 如果只是预留, 不要为了"让它有引用"硬塞进页面;
8. 跑校验, 重点看 DR-02, DR-03, DR-05, DR-10;
9. 重新生成 `reference.md`; 更新 `components.md` (如果引入了新的组件用法) 或 `semantic-layer.md` (如果改变了区域规则).

插入位置的实用做法: 先在 Light 中确定前一个键, 再在 Dark 中定位同一个键, 插入到它后面. 不要依赖行号或字母排序.

### 4.4 修改语义键值

1. 同一个键在两个主题里各改一次, 结构不动;
2. 只改值, 不改键名, 不改区块, 不改位置;
3. 检查该键在 Light/Dark 的对应角色是否仍然成立 (例如悬停态比默认态更突出);
4. 跑 DR-02 至 DR-05, 重新生成 `reference.md`;
5. 视觉验证所有引用该键的控件; 必要时更新 `components.md` 的说明.

### 4.5 重命名语义键

1. 全局搜索旧键: 视图, `Controls.xaml`, Bridge 的 owner 注释, 文档, 脚本注释;
2. 在 Light 的同一位置改名, 在 Dark 的同一位置改同样的名;
3. 同步所有引用方; Bridge owner 注释也要改, 否则 DR-12 会给警告;
4. 跑校验, 确认没有残留的旧键引用 (DR-09 会指出视图里的未定义键);
5. 重新生成 `reference.md`, 并搜索 `docs/` 修正文档中的旧键;
6. 如果旧键已经随版本发布, 在 PR 描述和发行说明里写一句重命名, 方便回看.

不要用"新增一个新键, 保留旧键"的方式做重命名; 那会制造两个含义相同的键. 除非有外部依赖无法一次性迁移, 而当前仓库没有这种依赖.

### 4.6 删除或废弃语义键

1. 全局搜索键名, 范围包括视图, 控件样式, Bridge owner, 脚本和文档;
2. **仍有引用**: 先迁移引用或先废弃. 废弃做法是保留键, 行尾加 `<!-- deprecated: 替代键或原因 -->`, 在 PR 里说明计划,
   等引用清零后再删;
3. **零引用且无发布兼容要求**: 在 Light/Dark 的同一位置删除;
4. **是预留键**: 确认 `components.md` 的预留清单和 `reserved` 标记一起清理;
5. **是 Bridge 键**: 确认没有原生模板依赖它, 或已经用新键替换; 删除前先在 Light/Dark 都删, 再跑校验;
6. 跑 DR-05, DR-09, DR-12, 重新生成 `reference.md`;
7. 更新文档里的引用.

不要因为"看起来没人用"就删: 先搜索. 图标, 别名, owner 注释都可能是引用点.

### 4.7 新增区域

1. 在 `scripts/check-design-system.ps1` 的 `RegionManifest` 中按 UI 顺序插入区域名; `ProductRegions` 会自动派生;
2. 判断它是不是组件区域. 只有真正跨页面复用的组件语言才加入 `ComponentRegions`;
3. 在 Light/Dark 的相同位置加入区块头和至少一个键, 区块头写 `区域 - 描述` 和 `Owner:`;
4. 如果现有视图需要引用它, 在 `ViewRegionMap` 对应前缀加入区域; 否则只对拥有它的未来视图开放;
5. 跑校验, 重点看 DR-03 (区块顺序, 键归属) 和 DR-11;
6. 重新生成 `reference.md`; 更新 `semantic-layer.md` 的区域表, 引用规则和视图映射表;
7. 区域名使用 PascalCase, 不能是禁用词; 新增区域属于结构变更, PR 描述里说明为什么现有区域不够用.

### 4.8 新增视图

1. 在 `Funzor/Views/` 下创建 XAML, 优先复用现有前缀 (页面放 `Views/Pages/`);
2. 在 `ViewRegionMap` 加一行, 路径匹配用完整文件或前缀, 区域只列真正需要的;
3. 颜色只用 `ThemeResource` 引本区域键, 尺寸用度量 token 或布局常量, 不写画刷和颜色字面量;
4. 如果用了原生列表并需要改状态色, 按[语义层](semantic-layer.md#53-视图别名)的别名模式, 在 Light/Dark 两个字典里写同样的键集合;
5. 跑 DR-06 至 DR-11; 重新生成 `reference.md`;
6. 如果是页面, 更新 `semantic-layer.md` 的视图映射表 (如果新增了路径类别), 并在 `components.md` 里补页面用法说明
   (如果引入了新模式).

未登记视图不会让构建失败, 只会得到 DR-11 警告, 且区域权限为空. 不要忽略这个警告.

### 4.9 新增控件样式

1. 先判断是否需要新样式: 同一外观出现两次以上, 或要沉淀为设计语言; 一次性局部外观不要加;
2. 在 `Controls.xaml` 新增样式, `BasedOn` WinUI 原生样式, 只设置尺寸, 圆角, 字号, 字重, 换行等; 不重写 `Template`;
3. 颜色用 `{ThemeResource ...}` 引语义键; 尺寸用 `{StaticResource A.*}`; 需要新颜色键时先走 4.3;
4. 命名与现有约定一致: 文本用 `{用途}TextBlockStyle`, 按钮用 `{变体}ButtonStyle`;
5. 跑校验 (`Controls.xaml` 允许所有产品区域, 但仍禁止颜色字面量和画刷); 重新生成 `reference.md`;
6. 更新 `components.md` 的样式表和使用规则;
7. 视觉检查 Light/Dark, 悬停/按下/禁用/焦点, 150% 缩放.

### 4.10 新增 Bridge 键

1. 确认原生控件确实需要这个键: 查当前 Windows App SDK 的 WinUI 资源, 不要凭记忆写;
2. 先确认 owner 语义键存在. 没有就先按 4.3 新增, 再回来做 Bridge;
3. 在 Light/Dark 的 `Bridge` 区块同一位置插入键, 值只引用 `A.*`, 行尾写 `<!-- owner: 区域键 -->`;
4. owner 必须能对应到具体键或键族; 对应不上时 DR-12 会给警告;
5. 跑校验, 重新生成 `reference.md`;
6. 运行应用验证原生控件的默认, 悬停, 按下, 禁用, 焦点状态;
7. 视图不要直接引用 Bridge 键; 如果确实需要, 说明理由并考虑加语义键, 而不是把原生键暴露给页面.

### 4.11 新增图标

1. 准备 256 viewBox 的 SVG, 放到 `Funzor/Assets/Icons/Source/`, 命名用 `{名称}_256_regular.svg`;
2. 在 `Icons.xaml` 新增 `Icon.{名称}` 的 `ControlTemplate`, 内部使用 256×256 坐标空间; fill 图标用 `Fill`,
   stroke 图标用 `Stroke`, 颜色都用 `TemplateBinding Foreground`;
3. 需要导航入口时, 把 key 写进 `NavigationCatalog`;
4. 构建并运行, 切换 Light/Dark, 确认未选中/选中/悬停颜色正确;
5. 图标 key 不存在时转换器返回 `null`, 图标静默空白, 不会报错; 因此必须肉眼确认;
6. 重新生成 `reference.md` (图标清单会自动更新), 必要时更新 `components.md`.

### 4.12 新增导航分区或页面

1. 新建页面类与 XAML, 页面标题通过导航参数或资源文案获取;
2. 在 `NavigationCatalog` 增加 `NavSection` 或 `NavEntry`, 文案 key 走 resw, 并保留内置中文回退;
3. 新增 resw 条目 (默认语言 zh-CN), 不要硬编码页面标题;
4. 页面位于 `Views/Pages/` 时通常不需要改 `ViewRegionMap`; 新增其他目录时按 4.8 登记;
5. 分区图标走 4.11;
6. 检查一级切换是否默认选中首项, 返回栈是否为空, 键盘能否走完整个导航;
7. 跑校验和构建, 重新生成 `reference.md`; 更新 `components.md` 的外壳说明 (如果外壳行为变了).

## 5. 双主题一致性

- 键集合, 数量, 顺序完全一致; 插入时对齐相邻键;
- 同一键在两个主题中承担相同角色, 不能 Light 是背景, Dark 是文字;
- `reserved`, `deprecated` 注释在两个主题里保持一致;
- `Default` 跟 `Dark` 走; 新增主题字典时同步 `Theme.xaml`, 并说明回退关系;
- 对比度靠人工检查, 重点: 正文 4.5:1, 大字号/图标 3:1, 实心按钮文字 4.5:1;
- 状态不能只用颜色表达; 错误, 成功, 警告要有文字或图标;
- 原生控件如果只在一套主题下变色, 优先怀疑 Bridge 键缺失或别名没有写全.

## 7. CI 与失败处理

PR 的 `.github/workflows/pr-check.yml` 会依次执行:

1. `scripts/check-design-system.ps1`: 设计系统规则;
2. `scripts/gen-design-reference.ps1 -Check`: 生成物是否最新;
3. `dotnet build`: x64 Debug 构建.

失败时先看规则编号和文件行号, 例如:

```
[error] DR-03 Funzor/Themes/Theme.Dark.xaml:123 第 88 个 key 顺序不一致: Light=Card.Border Dark=Card.Background
```

处理顺序: 定位规则 → 按第 9 节修 → 本地重跑检查 → 重新生成参考 → 再提交. 不要通过删规则, 放宽白名单或手改生成物来绕过.

本地可以输出机器可读报告:

```powershell
pwsh scripts/check-design-system.ps1 -Format Json -ReportPath design-system-report.json
```

## 8. 评审清单

提交前逐条确认:

- [ ] 变更属于哪一类, 是否只做这一类;
- [ ] 键的区域归属正确, 没有跨区域引用;
- [ ] 命名符合形状, 没有禁用段;
- [ ] 两个主题同位置, 同集合, 同顺序;
- [ ] 主题文件没有十六进制, 没有 `ThemeResource`, 只引用存在的 `A.*`;
- [ ] 视图颜色用 `ThemeResource`, 尺寸用度量 token, 没有画刷/`Color=`/`Transparent`;
- [ ] 视图别名在 Light/Dark 两个字典里键集合一致;
- [ ] Bridge 键 owner 有效, 视图没有直接引用 Bridge;
- [ ] 没有重写控件模板; 新样式基于原生样式;
- [ ] 运行了校验, 参考比对和构建;
- [ ] 运行检查覆盖 Light/Dark, 键盘, 缩放;
- [ ] `reference.md` 已重新生成且包含在提交里;
- [ ] 相关文档已同步更新;

## 9. DR 排查表

| 规则  | 含义                                               | 常见原因                                                | 修正                          |
|-------|----------------------------------------------------|---------------------------------------------------------|-------------------------------|
| DR-01 | token 必须 `A.` 开头, 颜色值必须是十六进制         | 新增 token 命名错, 颜色写成 `Red`                       | 改键名或改十六进制值          |
| DR-02 | Light/Dark 键集合, 数量一致且无重复                | 只改了一个主题, 复制粘贴重复键                          | 同位置补齐, 删重复            |
| DR-03 | 键顺序, 区块顺序, 键归属                           | 在末尾追加, 插错区块, 区块头写错                        | 对齐相邻键, 移回本区块        |
| DR-04 | 主题文件禁止十六进制                               | 直接把色值写进语义层                                    | 改为 `{StaticResource A.*}`   |
| DR-05 | 主题文件只允许 `StaticResource A.*`, 且 token 存在 | 用了 `ThemeResource`, 引用不存在的 token                | 改引用方式或补 token          |
| DR-06 | 视图禁止画刷, `Color=`, 颜色 token                 | 在页面里定义 `SolidColorBrush` 或直接引用 `A.Neutral.*` | 删除局部画刷, 改用区域键      |
| DR-07 | 视图禁止十六进制                                   | 页面里写了 `#RRGGBB`                                    | 改为区域键                    |
| DR-08 | 视图禁止 `Transparent` 字面量                      | `Background="Transparent"`                              | 用区域键表达透明              |
| DR-09 | 引用的键必须在两个主题中存在; WinUI 键必须在白名单 | 键名拼错, 只加了一个主题, 引用了未允许的原生键          | 补键或改白名单 (谨慎)         |
| DR-10 | 语义键命名形状                                     | 末段不是属性/状态, 出现禁用段                           | 按词表重命名                  |
| DR-11 | 视图必须登记区域, 不能跨区域引用                   | 新视图没加映射, 页面引用了导航键                        | 加 `ViewRegionMap` 行或改引用 |
| DR-12 | Bridge 键必须有有效 owner                          | 缺注释, owner 写错, owner 对应不上                      | 补 owner 或先补语义键         |

警告不阻止合并, 但必须处理: DR-11 的未登记视图, DR-12 的 owner 找不到键族, 都会让后续维护失去依据.

## 10. 检查盲区

以下内容脚本查不到, 必须人工确认:

- 视图内 Light/Dark 两个别名字典是否键集合一致;
- 视图是否直接引用了 Bridge 键;
- 颜色对比度, 色觉障碍可辨识性;
- 运行时资源是否真的解析成功 (脚本只解析文本);
- 硬编码尺寸是否合理, 是否该收敛为 token;
- 图标 key 是否存在 (不存在时静默空白);
- WinUI 原生控件在真实模板下的悬停/按下/禁用表现;
- `reserved` 键是否仍然有意义, 是否该转正或删除.

## 11. 文档自身如何维护

| 变更                            | 必须更新的文档                              |
|---------------------------------|---------------------------------------------|
| token 族, 档位, 类型约定        | `tokens.md`                                 |
| 区域增删, 区域顺序, 区域权限    | `semantic-layer.md`                         |
| 命名语法, 引用规则, Bridge 约定 | `semantic-layer.md`                         |
| 控件样式, 图标用法, 外壳规格    | `components.md`                             |
| 校验规则, CI, 维护流程          | `maintenance.md`, 必要时 `README.md`        |
| 任意键或值                      | `reference.md` (只重新生成)                 |
| 视图映射                        | `semantic-layer.md` + `reference.md` (自动) |
| 文档目录或阅读路径              | `README.md`                                 |

约定:

- 文档与代码同 PR; 不允许先合并代码, 文档留到下一次;
- `reference.md` 永远不手改; 差量由脚本产生;
- 手写文档不复制全量键值表; 引用具体键时写清楚区域和用途;
- 文档头部元信息随适用范围变化更新;
- 文档中的链接, 键名, 文件名应能被人工快速核对; 发布前按下面的自查清单核对链接和锚点.

提交前的文档自查:

1. `gen-design-reference.ps1 -Check` 无差异;
2. 搜索本次改动的旧键名, 确认文档没有残留;
3. 相对链接指向存在的文件, 锚点指向存在的标题;
4. 新增章节放进了正确的文档, 没有把流程写进用法文档.

## 12. 提交与发布记录

- 提交信息使用约定式前缀: `feat(theme)`, `fix(theme)`, `refactor(theme)`, `docs(design)`, `ci(design)`;
- 设计变更写清"为什么"和"影响了哪些区域", 不要只写"调整颜色";
- 发行说明由 `git-cliff` 按提交类型分组生成, 设计变更会进入"新功能/问题修复/文档"等分组;
- 设计系统没有独立版本号, 跟随应用版本; `reference.md` 是当前快照, 历史通过 Git 查看;
- 删除或重命名已发布过的键, 在 PR 描述和发行说明里注明, 避免回看时断线.

## 13. 升级 Windows App SDK 时

Bridge 键和白名单直接依赖 WinUI 资源, 升级前按以下清单审计:

1. 阅读 Windows App SDK / WinUI 的变更说明, 关注控件模板资源和键重命名;
2. 升级 `Microsoft.WindowsAppSDK` 后先跑设计系统校验和构建;
3. 运行应用, 逐项检查原生控件: 文本框, 按钮, 菜单, 对话框, 滚动条, 进度条, 工具提示;
4. 对照 `Bridge` 区块确认键仍有效; 无效的键补映射或删除, owner 同步更新;
5. 检查 WinUI 白名单里的文本样式是否仍存在; 检查项目同名样式 (`BodyTextBlockStyle`, `CaptionTextBlockStyle`) 是否仍符合预期;
6. 检查别名映射的 `ListViewItem*` 键是否仍被原生模板使用;
7. 更新 `reference.md`, 必要时更新 `foundations.md` 的已知限制和 `components.md` 的控件说明.

升级后如果视觉变化明显, 先判断是模板行为变化还是我们的 Bridge 缺键, 不要直接用局部样式打补丁.
